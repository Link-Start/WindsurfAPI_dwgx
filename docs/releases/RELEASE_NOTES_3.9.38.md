# v3.9.38

独立审计的 corrections 轮:七个已证实的缺陷修复,其中一处是数据保全。无 API 破坏、
无新功能面,走 patch。审计裁决为 `CHANGES_REQUESTED`,本轮逐项收口后重新出的门禁。

## 数据保全:代理工作区迁移不再删除无法证明属于自己的文件(最重要)

`ensureWorkspaceDir` 原本会"迁移旧脚手架":判据是 `package.json` 的 `name` **不等于**
`proxy-workspace-stub`——也就是"这不是我现在写的名字",然后对 `<工作区>/src` 做
**递归删除**,并覆盖 `package.json`、`README.md`、`.gitignore`。

独立审计用未修改的辅助函数源码在临时目录上实测:一个普通项目名(非 stub)的目录,`src`、
README、package.json **全部丢失**;仅名字叫 `my-project`、但内容已被人工修改的目录同样被删。

**"认不出"不等于"是我写的",所以迁移整体移除,而不是把判据写得更窄。** 现在只有本调用
自己创建的目录才会被写入;已存在的目录**一个字节都不动**。全新路径的创建行为不变——防止
模型把占位符当成用户工程的那条性质,继续由 stub 内容本身承担。

`test/workspace-scaffold-ownership.test.js` 用调用前后逐字节快照钉住这条规则(外加全新创建
的对照);同时删除了 `test/workspace-stub-108.test.js` 里那条按源码文本断言
`/isLegacyScaffold/` 和旧判据本身的测试——它钉的是实现,而且钉的正是这个缺陷,所以删除
而不是改写成新文本。其余三条 #108 守卫原样保留且全绿。

## 凭据库:解密必须用格式约定的 16 字节 GCM tag

一条凭据记录的 16 字节认证标签被截短到 4 字节后,**仍然能解出密码**。读取路径没有传
`authTagLength`,node 会按文件里带来的长度去认证,只发一条 DEP0182 警告——缩短标签这种
篡改被当成正常读入,而 GCM 标签的全部意义就是不可缩短。

写入侧本来就存完整的 128 位标签,所以长度属于这个文件格式,不是调用方偏好:标签字段现在
按恰好 16 字节校验,并且 `createDecipheriv` 显式收到 `{ authTagLength: 16 }`。今天写入器
产生的合法 v1 文件不受影响(往返、错主密钥、密文被改三条对照全部照旧)。

**明确不动**(审计把它们划到需要格式裁决的另一批):scrypt 的 N/r/p、AAD、记录与邮箱之间
的身份绑定。在没有版本化迁移证明之前提高 KDF 常量会让**每一个现存库都解不开**。

## 扫描器:一条基于真实路径的边界,覆盖全部三条输入路径

密钥扫描的边界原本是词法的(`relative(root, abs)`),而 junction 恰好能骗过词法判断:重解析
点的路径读起来在仓库内,目标却在仓库外。审计实测到三处不对称——显式指定的仓库内 junction
会被跟随后读到仓库外的文件;junction 出现在被扫描的父目录里时被**无声跳过**;而
`git ls-files -co` **自己就会穿过 junction**,所以连不带参数的默认扫描(也就是本地门禁每次
推送跑的那一步)都能读到仓库外的文件。

三条路径现在共用同一个基于真实路径的判据:留在仓库内的链接会被跟随(并记住真实路径,避免
成环),离开仓库的链接直接以 exit 2 拒绝——**"我们没看过那里"绝不能变成"看过且干净"**。

本仓库自己的 897 条默认输入路径全部落在仓库内,门禁步骤除了耗时(7.4 秒,原 ~2.6 秒)没有
变化。`test/secret-scan-links.test.js` 覆盖三条路径上的越界 junction、跟随内部链接的正向
对照、环、断链、外部绝对路径,以及"本仓库默认扫描仍然干净"的防过度拒绝对照。

## 历史覆盖:恢复路径不再虚报

`historyCoverage` 记录的是上游 prompt 实际带上了多少轮历史。它只在 fresh 路径计算:resume
失败后重建级联的 `rebuildFullHistoryText` 用同样的预算重新截断了同一份历史,却从不更新这个
数字,于是恢复前那个"全量"的值被原样返回——审计用真实客户端 + 回环假 LS 实测:恢复后的
wire 同样缺了最旧的几轮,元数据却报 `droppedTurnCount: 0`。

截断逻辑现在是一处闭包,两条路径共用,因此不可能对"到底送了什么"给出两个答案。prompt 文本
未变:预算单位、默认上限、上游请求形状一律未动。

## 鉴权:组合证明补到真实路由

G-1 的四个测试是纯函数测试(键阶梯、凭据提取、scope 规则)。审计在测试进程内把真实外层门
`src/server.js:415` 去掉后,它们仍然 4/4 通过——也就是说该文件头部声称的"组合"并没有被测到。

新增的真实路由器矩阵覆盖 4 条 `/v1` 路由 × 5 种凭据形态(无凭据、错 key、只有
`x-dashboard-session`、只有 `x-session-id`、两者都有)全部 401 `auth_error`,并用门后的哨兵
值(503 无活跃账号)作为"有效 key 通过了门"的对照。禁用外门时正好是这两条新测试变红,服务
器正常启动——失败原因是缺少拒绝,不是夹具坏了。

## 工程:门禁现在会测量 mutation baseline

两份 spec 的 `expectBaselinePass` 与实际不符:`s4-r4.json` 写 8 实测 9、
`think-text-reroute.json` 写 91 实测 95。两者都是"合并产物"——修复提交往别的 spec 已经
覆盖的测试文件里加了断言,而没人重测那两份 spec。没有任何东西能看见它:`npm test` 不跑
spec,而测量 baseline 的脚本导入的是 POSIX-only 的 git 解析,在这台机器上根本跑不起来。

全部 74 份 spec 已实测:4 处与配置不符,其中另两处(`ota-fixture-containment` 18+1 skip=19、
`self-update-hotfix` 113+51 skip=164)由本平台跳过解释,**它们的 Unix 期望值是正确的,没有
下改**。`scripts/spec-baseline-check.mjs` 把这条区分做成机械检查并进入门禁:接受
`pass + skipped === expectBaselinePass` 为平台差异,报告真实漂移并给出应设的值,**从不回写**
spec——漂移值是需要人裁决的事,自动回写只会把这个检查变成它本该抓住的那种漂移的橡皮图章。
另加一条静态上界(`spec-static-check`):pinned 值不得小于所覆盖文件声明的测试数,77 份
spec 上 69 份精确相等、8 份因循环生成而留白、0 违规。
